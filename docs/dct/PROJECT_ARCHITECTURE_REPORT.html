1. What QuickBite is

QuickBite is a food ordering and delivery platform (Swiggy / Zomato style) built as one monorepo. A customer places an order, a restaurant kitchen prepares it, and a rider delivers it. The product is designed so that handoff is real — not a single demo user with one flat UI.

  • Mobile app for customers and riders (Expo)
  • Web dashboard for restaurant managers, owners, and platform admins (Vite)
  • Marketing landing (Vite)
  • One shared backend — Supabase Auth, Postgres, RLS, Realtime, Edge Functions
  • RIO — JWT-scoped AI ordering assistant for customers

Core rule: Postgres is the authority. Order status, fees, delivery range (8 km), and roles are enforced in SQL (RLS + security-definer RPCs). Clients and RIO tools call the same rules — they do not bypass them.

3. System architecture (high level)

Apps talk to Supabase with the anon key + user JWT. The service role key stays on servers/scripts/Edge secrets only — never in EXPO_PUBLIC_* or VITE_*.

5. End-to-end order flow

placed → preparing → ready → out_for_delivery → delivered
         ↘ cancelled (from placed / preparing)
StepWhoMechanism
1. Kitchen open + menu availableManager / ownermenu_items, restaurants.is_open
2. Browse / cart / checkoutCustomerSafe views + cart_items → RPC place_order → placed
3. Accept → prepare → readyKitchenRPC restaurant_set_order_status
4. Assign riderClaim or auto on readyclaim_delivery / trigger auto_assign_rider
5. Out for delivery → deliveredAssigned riderRPC rider_set_order_status
6. RateCustomerInsert into ratings (one per delivered order)
  • Accept timeout: ignored placed orders older than config (default 30 min) auto-cancel via run_order_accept_timeout + pg_cron.
  • Delivery range: place / cart / RIO confirm blocked outside 8 km of the kitchen.
  • Payments (product scope): cash-only for the assignment.
  • Clients never UPDATE orders directly — status changes only through RPCs.

6.4 RIO tools (customer AI)

Discovery path: vague ask → browse_themes → theme → find_offers → kitchen → get_menu → cart → checkout.

  • Discovery: browse_themes, find_offers, verify_dish (plus thin find_food alias)
  • Menu / cart: get_menu, cart (view / add / set_qty)
  • Checkout: two-step confirm with cartHash (CART_CHANGED guard) → place_order
  • After order: order_status, report_issue, reorder_last, save_prefs

Product physics inside RIO: one kitchen per cart, 8 km delivery, prefer open kitchens, never invent prices/statuses, degrade calmly on tool/LLM failure. Shared memory: last ~8 turns in rio_messages + durable profiles.rio_memory.

7. Security model

  1. RLS on every business table
  2. Named policies open specific doors
  3. Order mutations only through RPCs (no client INSERT/UPDATE/DELETE on orders / order_items)
  4. Customers browse via safe views; riders see unclaimed jobs via redacted RPC
  5. Role / email changes blocked on client (profiles_guard_update)
  6. RIO uses the user JWT so tool calls obey the same RLS as the app

8. Auth

  • Email & password signup / login (customer + dashboard)
  • Google OAuth via Supabase Auth
  • Signup always creates profiles.role = customer via handle_new_user
  • Manager AuthGate: admin → /admin, owner/manager → kitchen shell, others → /blocked
  • Expo routes customer vs rider tabs from profiles.role
  • Redirects: Vercel dashboard origin + Expo scheme quickbite://
